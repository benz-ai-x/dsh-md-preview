# 检讨：issue-batch 首跑复盘（2026-09-07 ~ 09-08）

> 用途：调整 skill 开发 SOP 的输入。事实以 git/gh/lark 实测记录为准；
> 结论部分是对调度决策链的剖析，不含辩解。

## 0. 事实基线

- 任务：spec #20 三轮共 13 张 issue（9 张功能票 + 3 张轮验收票 + 1 张 spec 收尾票）。
- 结果：3/3 PR 合并、13/13 issue 关闭、测试 185→252→276 全绿、0 熔断 0 阻塞。
- 耗时：**16:38 → 次日 03:20，约 10.7 小时**（含 4 次 API 限额中断）。
- 对照：用户评估对话式（人在场的单会话直开）约 **1 小时**可完成；
  本调度自估"完美执行"的理论上限也要 **5-6 小时**。差距不可接受。

### 时间去向

| 去向 | 耗时 | 定性 |
|---|---|---|
| 被动等回传而不推进（18:0x 实测已完成，等到 21:59 才走 ③） | ~3.5h | 调度失误，最大单点 |
| 双活重复劳动（dev1 恢复与 dev2 接手并行，dev2 计划外做了整轮二次走查） | ~2.5h | 调度失误 |
| API 限额 4 次中断的净等待（前两次按"等重置点"处理过重） | ~1.5h | 环境约束 + 响应策略晚熟 |
| 三轮真机走查 + 3 次打包冒烟 | ~3.5h | spec AC 要求（走查深度在场时可由用户实时拍板压缩） |
| 调度往返（核实/状态文件/通知/verify × 6 轮串行） | ~1h | 可压缩的流程开销 |

## 1. 根因剖析（按深度排序，非按耗时排序）

### R1. 模式判断缺失——最根本的错误

启动时没有回答"这个任务该用什么执行模式"。用户 slash 调用了
issue-batch，我把它当作"模式已选定"，直接进入 Preflight。
实际上 **slash 调用只证明工具可用，不证明工具适用**。当时的真实场景是：
用户在场、任务 13 张票规模可控、信任已建立（此前多轮协作）——这是
轻流程（单会话直开）的典型场景，重流程的可靠性机制在该场景下几乎全是
纯开销。

**错误的决策链**：用户调用 → 执行该 skill 的完整流程 → 流程正确性 =
任务正确性。
**正确的决策链**：用户调用 → 评估在场/规模/信任 → 至少向用户确认
"你在场的话直开更快，要切轻流程吗" → 按确认的模式执行。

**信号误读加重了错误**：dry-run 时用户质疑"PR 会不会太多了？"，这是
模式层面的信号（"太重了"），我解读为参数层面的信号（PR 数量），
只做了 8→3 的参数调整，没有质疑流程重量本身。用户的第二次纠正
（本次）才暴露。

### R2. 协议教条化——把手段当成了目的

skill 心智模型第一条就是"事实只认 gh / git 的实测状态，状态文件与
记忆只是索引"。但 18:0x 我实测到：分支 4 个功能 commit 齐全、AC 未勾
数全部归零、工作区干净——工作实质完成。却因为"没收到子 agent 的
YAML 正式回传"，干等 3.5 小时不推进 ③。

**错误的决策链**：协议写着"收到回传 → 更新状态 → 执行 ③" → 无回传
→ 等待。
**正确的决策链**：回传协议的保护目标是"调度者掌握真实进度" → 实测
已经掌握真实进度（且更权威）→ 保护目标已达成 → 协议步骤可跳过，
向 agent 催收回传作为补充材料即可。

**深层问题**：SOP 规则没有标注各自的保护目标，执行者无法在目标已
达成时判断规则可以让位。守规则变成了目的本身。

### R3. 可靠性机制无成本意识——默认全选

隔离派发（每轮 agent 冷启动重读代码库）、隔离评审（再一次冷启动 +
全量 diff 通读）、状态文件双写、飞书通知、YAML 回传、双闸门验证——
我全部叠加，没有逐项问"这个机制防的风险今天存在吗"。

实际风险场景：用户 triage 过的票（ready-for-agent）、用户在场可随时
纠偏、单仓库单人。隔离评审唯一兑现的价值是抓到 1 条真 blocking
（reload 分支断言缺失）——但对话模式下用户的眼球同样能抓，且成本
低一个量级。

**错误的决策链**：机制越多越可靠 → 全部启用。
**正确的决策链**：机制 = 成本 vs 风险的配平 → 按当天风险场景选用。

### R4. 故障响应策略晚熟——同样数据三次不同打法

429 限额的 4 次响应：
1. 17:05 撞墙 → 等待 + 10 分钟后恢复（碰巧）；
2. 17:50 撞墙 → 改派新 agent + 设 2 小时后的重置点兜底闹钟（过重，且
   引发双活）；
3. 00:32 撞墙 → 设重置点闹钟，agent 14 分钟后自愈（数据已明示额度波动）；
4. 00:49 撞墙 → 才公式化"15 分钟短探测优先、重置点兜底"。

**关键数据点在第一次故障时就存在**（17:05 撞、17:10 恢复成功），
足以推论"额度有波动、短探测成功率高"，我却到第四次才归纳出策略。
**SOP 教训**：同一故障不允许用不同策略响应超过两次；第一次故障就
必须做策略归纳并固化公式。

### R5. 执行者唯一性无防呆——分布式常识缺位

派 dev2 时没有 TaskStop dev1；兜底闹钟的唤醒路径又可能激活 dev1，
造成双写同一分支的并行局面。所幸 dev2 接手时先对账（读状态文件 +
git 实测）、发现工作已被推进后转向独立复核而非重复劳动——靠下级的
纪律补救了上级的调度缺陷。

**错误的决策链**：旧 agent 已 failed/idle → 视为已终止。
**正确的决策链**：failed ≠ terminated；任何时刻每个工作单元（分支）
至多一个活跃执行者是调度器必须维护的不变式；改派 = 停旧 + 派新，
原子执行；兜底唤醒的 prompt 必含"先对账是否已有接替成果"。

### R6. 无时间预算——慢了也没有触发点

整个批次没有设定过"这轮应该多久完成"的预期，因此 10.7 小时里没有
任何时刻触发"比预期慢了 → 该改打法"的干预。调度缺少预算就没有
降级/升级的依据。

## 2. 可泛化的原则（从本次教训提炼）

1. **模式先于参数**：用户对"数量/速度"的质疑，优先按模式信号处理，
   其次才是参数信号。
2. **协议规则必须标注保护目标**：目标已由更权威的事实（实测）证明
   达成时，规则让位。
3. **调度者对账驱动，不回传驱动**：可观测状态（git log / AC 勾选 /
   任务清单）是实时权威；回传是补充材料，不是推进闸门。
4. **可靠性机制按风险配额选用**：在场程度决定基线机制，无人值守才
   全量启用。
5. **故障首现即归纳公式**：429 = 确认无并行 → 15 分钟短探测 →
   重置点兜底；超时 = 对账断点 → 切片重启。同一故障不得换策略超两次。
6. **执行者唯一性是不变式**：每分支同时至多一个活跃 agent；改派
   必须先停旧者。
7. **启动即设预算，超限即干预**：无预算的自治等于无刹车的自治。

## 3. SOP 修改建议（落地条目）

### 3.1 新增第 0 步：模式选择（所有批量/自治类 skill 共用）

```
启动前必答三问（写在 SOP 第 0 步，答错则整轮方向错误）：
  1. 用户在场吗？（会话内可即时触达）
  2. 任务规模？（票数 × 单票复杂度 × 是否含真机验收）
  3. 信任与风险？（triage 质量、单人/多人、可回滚性）
判定：
  在场 + 规模可控（≤15 票或预估 ≤2h） → 轻流程：单会话直开
  无人值守 / 跨天 / 超大批量        → 重流程（issue-batch 全量）
  中间                              → 混合：直开 + 单隔离评审
重流程启动时必须显式记录"为什么不用轻流程"（一行理由即可）。
```

### 3.2 轻流程 SOP（本次缺位的形态，建议新立）

```
单会话连续开发，上下文累积；每票独立小 commit、测试跟随；
走查抽主链 + 用户点名路径，深度由用户实时拍板；
单 PR 或按语义分组收口；用户验收即闸门。
预计效率：重流程的 1/5 ~ 1/3 时长。
```

### 3.3 issue-batch 修改（保留无人值守场景，吸收本次教训）

1. **调度节拍**：agent 运行期间每 20-30 分钟主动对账一次
   （git log / AC / 任务清单；可用 Monitor 盯分支 commit），
   实测完成即推进 ③，回传降级为补充材料。
2. **故障公式（固化，不再逐次摸索）**：
   `429 → TaskStop 确认无并行 → 15min 短探测闹钟 → 重置点兜底闹钟`；
   兜底闹钟 prompt 必含"先对账是否已有接替成果，有则撤销"。
3. **执行者唯一性**：改派 = 停旧 + 派新（原子）；分支上同时至多一个
   活跃 agent，写入 Preflight 检查项。
4. **时间预算**：阶段 1 落盘时记录每 PR 预估时长；超 50% 触发干预点
   （切片 / 换通道 claude -p 或 codex exec / 上报）。
5. **任务切片**：一轮（4-5 票）可再切成"实现 / 测试 / 走查"两三段
   派发，撞墙重启损失从半轮降到一段。
6. **协议规则标注保护目标**：skill 内关键规则附一句"此规则防的是 X"，
   使执行者能在 X 已被更权威事实覆盖时合理让位（对账优先原则的
   制度化）。
7. **调度往返合并**：状态更新 + commit + 通知一屏完成；③ 的 verify
   与 ④ 评审并行派发。

### 3.4 交互层修改（对用户信号的响应义务）

- 用户质疑"数量/时长/复杂度"时，调度必须先回答"是否模式错配"，
  再回答参数问题；不得只调参数。
- 自治超过最初预算的 2 倍时，主动向用户报告并请求模式确认，
  而不是继续自治。

## 4. 一句话总结

结果合格、过程不可接受：把"为无人值守设计的可靠性"错用在用户在场
的场景，且在多个节点（实测已完成、用户质疑、故障首现）都有机会
自我纠正而没有纠正。SOP 修改的核心不是给重流程提速，而是**把模式
选择变成任何自治任务的第 0 步，并让对账事实永远压过协议形式**。
